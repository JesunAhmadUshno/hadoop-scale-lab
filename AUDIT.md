# Audit (the study report)

This file is the report in the portfolio standard's sense. It keeps
the name AUDIT.md because the locked PREREGISTRATION.md names it as
the place where co-tenancy during runs is recorded.

Status, 2026-11-11: Phase 3 is complete. The timed matrix ran on
the machine of record (Dell R610, Ubuntu 24.04.5, 94 GiB RAM,
16 cores) on 2026-11-08 and 2026-11-09 (Phase 2), and the one
cell Phase 2 left unmeasured, the H2 small-file cell, was
measured on 2026-11-11 under the owner's explicit authorization
(DECISIONS.md D15, D16). The compose cluster was torn down at
each close. Verdicts, computed by
scripts/make_results.py from results/raw_runs.jsonl under the
rules frozen in PREREGISTRATION.md: H1 CONFIRMED, H2 CONFIRMED
(small-file cost 1251.7 percent: median 7737.209 s over 1,055
files against the combined layout's 572.420 s over 9 files),
H3 INCONCLUSIVE (write penalty 29.5 percent, job penalty -0.1
percent), H4 REFUTED (Spark median 1087.0 s against the MapReduce
median of 954.5 s). RESULTS.md carries the full tables.

## How the evidence is protected

1. Pre-registration before results. PREREGISTRATION.md is the
   first content commit (d06513e), written before any code,
   corpus processing, or run existed. Git history shows the
   order, and a test pins the file to its locked hash.
   PREREGISTRATION.md was not edited during Phase 2; every
   adaptation lives in DECISIONS.md (D4 to D14), each recorded
   before the runs it affected.
2. Correctness before speed, in code. The Phase 2 driver
   (scripts/run_study.py) hashes every run's canonical output
   and voids the cell on any mismatch with the baseline; the
   void is written to the raw run log. Across the full run log
   (64 run records: 16 warm-up, 48 timed), zero runs are marked
   void and every timed run's hash equals its baseline
   reference, including all four Spark runs and the four
   Phase 3 small-file runs. One record is a void_cell: the
   Phase 2 stop of the H2 small-file cell (D11), kept as
   history; the cell it names was measured in Phase 3 (D15,
   D16). The same equality is exercised without a
   cluster by tests/test_equivalence.py: both jobs, through a
   local pipe, match the DuckDB baseline byte for byte after
   canonical sorting, including a zero-token document and
   Unicode text, and on a real-corpus slice of 20,000 documents.
3. One tokenizer, both arms. src/common.py is imported by the
   Streaming jobs (shipped with -files), by the Spark job
   (shipped with --py-files, DECISIONS.md D14 addendum 3), and
   by the baseline, so tokenization cannot drift between arms.
4. Corpus integrity. One file, downloaded from the pinned dated
   dump directory; MD5 verified against the publisher's
   checksum file by scripts/fetch_corpus.sh; SHA-256 recorded
   in results/corpus_manifest.json before any run, and
   re-verified on the R610 on arrival in Phase 2. The
   extraction manifest is committed as
   results/extraction_manifest.json: 648,182 documents,
   1,984,437,310 bytes of extracted text.
5. Numbers come from scripts. RESULTS.md is generated by
   scripts/make_results.py from results/raw_runs.jsonl,
   results/host_state.json, and results/layouts.json, and CI
   fails if the committed RESULTS.md differs from a fresh
   regeneration. Medians, ratios, penalties, and verdicts in
   RESULTS.md and in this report are the script's,
   cross-checked by hand arithmetic.
6. No substitute machines. Every timed cell ran on the R610.
   Development machines ran correctness checks only, which
   carry no times.
7. Spend and credentials. Zero spend: every tool is local and
   open source; the corpus is a public dump. No credential was
   created. The R610 password was never written to any file in
   this repository. The standalone Python tarball used by the
   Spark executors (D14) is a public release artifact, recorded
   with its SHA-256.

## Deviations and incidents on record

Phase 1 items, still standing:

- DECISIONS.md D1: the corpus is the English Wikisource articles
  dump, not the brief's recommended Wikipedia abstracts dump,
  because Wikimedia no longer publishes abstract dumps (the
  historical URL returns 404, verified 2026-11-08). The brief's
  fallback rule (real text, one file, checksum, nested subsets)
  is followed exactly.
- DECISIONS.md D2: zero-token documents fall in no length band;
  both arms exclude them identically via the shared band
  function.
- Download incident, 2026-11-08: the first corpus download's
  connection dropped and a plain curl --retry restarted the file
  from zero; a size-only check briefly read the file as
  complete. The MD5 gate in scripts/fetch_corpus.sh caught the
  bad state (hash mismatch, nothing recorded), the file was
  re-downloaded, and the final copy verifies exactly against
  the publisher's MD5 (4f0f5f9704207360eaa9471fb088acd3) with
  SHA-256
  bb9318dd1045cd0e0f0e5ea9329b1d61a639590758427fd4275a2926fa6a5272
  in results/corpus_manifest.json. The fetch script now resumes
  (-C -) instead of restarting. A full bzip2 stream test of the
  final copy also passes.

Phase 2 items, each in DECISIONS.md, each recorded before the
runs it affected:

## Co-tenancy during runs

The R610's other duties stayed live throughout Phase 2, as the
brief for the machine required: the Penpot design server
(8 Docker containers, port 9001), Cockpit on 9090, xrdp on
3389, an n8n instance, and Docker generally, plus the host's
scheduled jobs named in DECISIONS.md D3 (a nightly backup at
03:15 UTC and an hourly baseline check from the P23 recovery
tests). The cluster itself ran under the frozen caps: deployed
totals 7 CPUs and 21.5 GiB, at or under the frozen 8 CPUs and
24 GiB. results/host_state.json records the host snapshot taken
at preflight. All other services were verified untouched at
teardown, and the compose project (hadoop-scale-lab) was the
only stack stopped or removed.

Phase 3 (2026-11-11) ran under the same conditions: the same
services stayed live while the small-file cell executed
(ingest from 05:50 UTC, timed runs to 14:34 UTC), the cluster
ran under the same deployed caps (7 CPUs, 21.5 GiB), and the
D3 start gate held run starts out of the backup window and
the first five minutes of each hour (it fired once, at
08:04 UTC). The runs are about 2.15 hours each, so the
host's scheduled windows were crossed during execution; that
is inherent to a cell of this length and is recorded here
rather than hidden. At teardown the compose project was
removed completely (containers, volumes, network) and the
other services were verified again: Penpot answers HTTP 200
on port 9001 with all 8 containers up, Cockpit listens on
9090, xrdp on 3389, and the host was not rebooted.

## Threats to validity

- One machine, one shared host. The R610 also runs Penpot,
  Cockpit and n8n, and the scheduled jobs named above. Medians
  of three blunt co-tenancy noise; no verdict sits within noise
  of its pass line except H1, whose ratio 0.963 stands 3.7
  percent under the 1.0 line.
- Pseudo-distributed cluster. All daemons share one host's
  disks and network, so HDFS replication and shuffle cost less
  network time than on separate machines. The result is claimed
  for this configuration, not for a multi-node cluster.
- The ladder tops out at 1.85 GiB, not the frozen 5 GiB (D7).
  H1 and H4 are decided at a smaller scale than planned; the
  crossover could move again above this range and this study
  does not measure that.
- Three timed runs per cell give a median and a range, not a
  confidence interval.
- The baseline is one tuned design (DuckDB, one process, token
  rows staged through a temporary CSV, which is part of its
  measured cost). A different single-node design could be
  faster or slower. On this machine it also ran DuckDB 1.4.3
  rather than the pinned 2.0.0 (D4).
- The two arms did not run the same interpreter (D5): Streaming
  tasks on Python 3.6.8, the baseline on Python 3.12.3. The
  final matrix is checksum-clean, so no measured cell shows a
  divergence; the asymmetry is recorded, not hidden.
- H2's margin dwarfs its noise. The measured cost (1251.7
  percent) stands about 83 times above the 15 percent pass
  line, and the three timed runs span only 37 s (0.5 percent)
  around their median, so co-tenancy noise, the crossed
  scheduled windows during the long runs, and the
  pseudo-distributed configuration cannot plausibly move
  this verdict. The claim is for this frozen configuration
  (1 MiB files, 4 reducers, the deployed caps) on this host,
  not for small files in general.
